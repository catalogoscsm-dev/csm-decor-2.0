Sumário Executivo — Para quem não é técnico

Realizamos uma varredura completa de segurança no site CSM Decor e encontramos 8 vulnerabilidades. Duas delas permitiam que qualquer pessoa com uma conta no site executasse código malicioso para roubar dados de outros usuários — e foram corrigidas imediatamente. As outras 6 estão documentadas neste relatório com prioridade de correção clara. Nenhuma credencial bancária ou dado financeiro está em risco direto, mas dados de perfil e sessões de usuário precisam de atenção. Este documento explica cada problema com linguagem simples, analogias do mundo real e mostra exatamente o que foi feito.

3. Vulnerabilidades de Alta Severidade — Corrigidas

🔴 Alta Falha #1 — Stored XSS via campo Instagram do Perfil perfil.html · linha 394 ✓ Corrigido
Analogia — Como entender isso

Imagine que você vai a um banco e preenche uma ficha com seu nome. O atendente pega a ficha e lê em voz alta para toda a agência. Se alguém escrever na ficha: "Meu nome é João. TODOS LEVANTEM AGORA!" — o atendente grita o comando para todos. O XSS funciona igual: o site "lê em voz alta" para o navegador qualquer coisa salva no banco, sem verificar se é texto normal ou código malicioso.

O que estava errado: O handle do Instagram do usuário era buscado do banco de dados (Supabase) e inserido diretamente na página via innerHTML, sem nenhuma verificação. Se alguém salvasse código JavaScript no lugar do handle, esse código seria executado pelo navegador de qualquer pessoa que visitasse o perfil.

O que um atacante poderia fazer:

  • Roubar o cookie de sessão de outros usuários logados
  • Redirecionar a vítima para um site falso (phishing)
  • Fazer ações no site em nome da vítima sem ela saber
  • Capturar senhas digitadas enquanto a página infectada está aberta
🔴 Alta Falha #2 — Stored XSS via Foto de Perfil (photo_url) perfil.html · linha 447 ✓ Corrigido
Analogia — Como entender isso

Imagine um cartão de visita. Você coloca o nome dentro de aspas: "Nome: João". Agora imagine que o João escreve no nome dele: João" cargo="Diretor. Ao copiar o nome entre aspas, você acidentalmente criaria: "Nome: João" cargo="Diretor" — inventando um campo que não existia. É exatamente isso que acontecia com o campo de foto: uma aspa mal colocada permitia "inventar" atributos HTML — incluindo um que executa código.

O que estava errado: A função esc() local de perfil.html não escapava aspas duplas ("), apenas < e >. Isso permitia que um valor de foto contendo " onerror=" quebrasse para fora do atributo src e injetasse um novo atributo HTML com código executável.

Agravante: Qualquer usuário pode atualizar seu próprio photo_url direto na API do Supabase usando apenas seu próprio token de acesso (que está disponível no browser do usuário logado).

4. Vulnerabilidades de Média Severidade — Pendentes

🟠 Média Falha #3 — Credenciais do Supabase no Histórico Git supabase-config.js · .gitignore ○ Pendente
Analogia — Como entender isso

É como gravar um vídeo de segurança mostrando onde a chave reserva da sua casa está escondida e depois publicar esse vídeo no YouTube. Mesmo que você apague o vídeo depois, alguém pode ter feito download. O Git funciona igual: cada commit é permanente no histórico. Uma vez que uma chave secreta entra no repositório, ela nunca mais é verdadeiramente secreta.

O que foi encontrado: O arquivo supabase-config.js contém a URL e a anon key do banco de dados. O próprio arquivo tem um comentário dizendo "Este arquivo não deve ser commitado" — mas ele não está no .gitignore, o que significa que já foi ou será enviado ao repositório remoto.

Por que a anon key importa: Ela permite que qualquer pessoa faça requisições diretas ao banco via API REST — criar contas em massa, testar políticas de acesso (RLS), e se alguma tabela tiver uma política permissiva, ler ou escrever dados livremente.

Como corrigir: Adicionar supabase-config.js ao .gitignore imediatamente. Considerar rotacionar a anonKey no painel do Supabase.

🟠 Média Falha #4 — Content Security Policy com unsafe-inline (proteção nula) vercel.json · linha 32 ○ Pendente
Analogia — Como entender isso

O CSP é como um segurança na porta de uma festa com uma lista de convidados. Mas unsafe-inline é como dizer ao segurança: "Pode entrar qualquer pessoa que estiver dentro do salão." A lista existe, mas não filtra ninguém que já esteja lá. As falhas de XSS (#1 e #2) não seriam bloqueadas pelo CSP mesmo se configurado, porque unsafe-inline permite scripts inline incondicionalmente.

O que está errado: O vercel.json tem um CSP configurado, o que é ótimo — mas ele inclui 'unsafe-inline' na diretiva script-src. Isso cancela completamente a proteção contra XSS, que é o objetivo principal de um CSP.

Por que isso existe: O site tem muitos scripts inline no HTML. Para remover o unsafe-inline, todos esses scripts precisam ser movidos para arquivos externos (.js) — o que é um refactor maior, mas necessário a longo prazo.

5. Vulnerabilidades de Baixa Severidade

🟡 Baixa Falha #5 — Scripts CDN sem Verificação de Integridade (SRI) produtos.html · produto.html · perfil.html ○ Pendente
Analogia — Como entender isso

Você pede um remédio na farmácia. Confiam na distribuidora e não abrem cada caixa. Um dia, alguém no meio do caminho substitui o remédio por veneno mantendo a embalagem original. O SRI resolve isso com um lacre numerado: se o número não bater, o remédio não é dispensado — mesmo que a embalagem pareça idêntica.

Onde: Em produtos.html, produto.html e perfil.html, scripts como GSAP e Supabase são carregados de CDNs externos sem o atributo integrity. O index.html já tem SRI correto — as outras páginas precisam receber o mesmo tratamento.

Como corrigir: Adicionar integrity="sha512-..." e crossorigin="anonymous" em cada tag <script> externo. O hash pode ser obtido em srihash.org ou diretamente no CDN.

🟡 Baixa Falha #6 — Dados Pessoais Enviados ao formsubmit.co (LGPD) fale-conosco.html ○ Pendente
Analogia — Como entender isso

É como entregar as cartas dos seus clientes para um correio terceirizado sem saber onde eles armazenam as cópias, quem tem acesso, ou por quanto tempo guardam. A LGPD (Lei Geral de Proteção de Dados) exige que você saiba e controle como os dados dos seus clientes são tratados por terceiros.

Os formulários de contato (nome, e-mail, telefone, mensagem) são enviados para o serviço formsubmit.co, que os recebe, armazena temporariamente e reencaminha por e-mail. Não há contrato de DPA (Data Processing Agreement) com esse serviço — um requisito da LGPD para qualquer empresa que processe dados de terceiros em seu nome.

Como corrigir: Migrar o envio dos formulários para uma solução própria (função serverless no Vercel, por exemplo) ou assinar um DPA formal com o formsubmit.co.

🟡 Baixa Falha #7 — Política de Senha Mínima Bypassável via API auth.js · linha 177 ○ Pendente
Analogia — Como entender isso

O segurança na porta exige documento para entrar. Mas há uma janela dos fundos sem segurança. A validação de senha no JavaScript só funciona para quem usa a interface do site. Quem enviar a requisição diretamente para o servidor (via curl ou Postman) ignora completamente essa regra — e pode criar uma conta com senha 1.

Como corrigir: Configurar a política de senha diretamente no Supabase Dashboard → Authentication → Security → Password strength. A regra definida lá é aplicada no servidor — não pode ser burlada via API.

6. Informativa

ℹ Info Falha #8 — Cliente Supabase Autenticado Exposto Globalmente auth.js · linha 709 ○ Pendente
Analogia — Como entender isso

É como o cofre do gerente bancário ser visível pela janela da rua. O cofre está trancado (as permissões do banco de dados protegem os dados), mas qualquer um na calçada pode ver que o cofre existe, qual modelo é, e tentar testá-lo. Remover o cofre da janela não resolve o problema de segurança do cofre, mas elimina informação desnecessária para potenciais atacantes.

O objeto window.CSMAuth.supabase expõe o cliente Supabase autenticado como uma variável global acessível pelo console do browser. Isso significa que um usuário logado (ou código JavaScript injetado via XSS) pode rodar comandos como CSMAuth.supabase.from('profiles').select('*') diretamente pelo console — com o JWT do usuário logado, enumerando a API e testando políticas de acesso (RLS).

Como corrigir: Remover supabase: _sb de window.CSMAuth em auth.js:709.

7. Correções Aplicadas Nesta Sessão — Antes e Depois

As duas vulnerabilidades de alta severidade foram corrigidas imediatamente após a descoberta, na mesma sessão de auditoria. Ambas utilizaram a mesma estratégia: substituir interpolação de strings com innerHTML por DOM API — a forma mais segura de inserir dados do usuário em uma página web.

Correção #1 — XSS via campo Instagram

A correção usa duas estratégias combinadas para máxima segurança: (1) o handle é filtrado por uma lista branca — só caracteres válidos de um handle Instagram passam; (2) o link é construído via DOM API, nunca por concatenação de strings em HTML.

❌ Antes — Vulnerável (perfil.html:394)
var instaHandle =
  user.instagram.replace(/^@/, '');

socialEl.innerHTML =
  '<a href="https://instagram.com/'
  + instaHandle + // ⚠ livre
  '">@' + instaHandle + '</a>';

// qualquer string vira HTML
✓ Depois — Seguro
var instaHandle = user.instagram
  .replace(/^@/, '')
  .replace(/[^a-zA-Z0-9_.]/g, '')
  .slice(0, 30);

var link = document.createElement('a');
link.href = 'https://instagram.com/' + instaHandle;
link.appendChild(document.createTextNode('@'+instaHandle));
socialEl.appendChild(link);

Correção #2 — XSS via foto de perfil (photo_url)

O avatar foi reescrito para criar o elemento <img> via DOM API. Ao definir img.src = valor como propriedade JavaScript (em vez de interpolar em uma string HTML), o browser trata o valor como URL pura — aspas e outros caracteres especiais não têm poder de injetar HTML.

❌ Antes — Vulnerável (perfil.html:447)
wrap.innerHTML =
  '<img src="'
  + user.photoUrl + // ⚠ aspas
  '" alt="' + user.name + '"'
  + 'onerror="...">';

// " no photoUrl quebra o
// atributo src e injeta código
✓ Depois — Seguro
var img = document.createElement('img');
img.src = user.photoUrl; // URL pura
img.alt = user.name || '';  // texto puro

img.addEventListener('error', function() {
  var div = document.createElement('div');
  div.textContent = primeiraLetra;
  wrap.appendChild(div);
});

Correção Bônus — Função esc() corrigida (defesa em profundidade)

A função esc() de perfil.html não escapava aspas duplas ("), ao contrário da versão correta em auth.js. A versão foi corrigida para incluir este escape — garantindo que, mesmo que algum innerHTML use esc() no futuro, ele seja seguro.

❌ Antes — Incompleta
function esc(s) {
  return String(s||'')
    .replace(/&/g, '&amp;')
    // ⚠ aspas " não escapadas!
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;');
}
✓ Depois — Completa
function esc(s) {
  return String(s||'')
    .replace(/&/g, '&amp;')
    .replace(/"/g, '&quot;') // ← adicionado
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;');
}

10. Conclusão

A auditoria encontrou 8 vulnerabilidades reais e concretas — não hipotéticas. As duas de maior risco (Stored XSS via instagram e Stored XSS via photo_url) foram corrigidas na mesma sessão, com código publicado no repositório.

As 6 vulnerabilidades restantes estão documentadas com prioridade, arquivo exato e estimativa de esforço. As três primeiras da lista de pendências podem ser resolvidas em menos de 20 minutos — especialmente adicionar supabase-config.js ao .gitignore.

Mensagem central: Segurança não é um estado definitivo — é um processo contínuo. Esta auditoria é um passo importante, mas deve ser repetida a cada nova funcionalidade adicionada ao site. O custo de corrigir uma vulnerabilidade antes do site ir ao ar é dezenas de vezes menor do que depois de um incidente.
